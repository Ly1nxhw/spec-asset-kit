## 清单用途

**核心概念**：检查清单是“需求写作的单元测试”。它检查需求是否完整、清晰、一致、可衡量、覆盖充分，而不是检查实现是否已经工作。

不要写实现验证项，例如：

- 不要写“验证按钮可以点击”
- 不要写“测试错误处理正常”
- 不要写“确认接口返回 200”
- 不要检查代码是否符合规格

应该写需求质量检查项，例如：

- 是否为所有卡片类型定义了视觉层级要求？
- “突出展示”是否用明确尺寸或位置量化？
- 所有交互元素的悬停状态要求是否一致？
- 是否为键盘导航定义了无障碍要求？
- 是否定义了图片加载失败时的降级行为？

## 用户输入

```text
$ARGUMENTS
```

如果用户输入非空，你**必须**先纳入考虑再继续。

## 执行前检查

**检查扩展钩子（生成清单之前）**：

- 检查项目根目录下是否存在 `.specify/extensions.yml`。
- 如果存在，读取 `hooks.before_checklist` 下的条目。
- YAML 无法解析时静默跳过。
- 过滤 `enabled: false`。
- 不要解释或求值 `condition`。
- 对每个可执行钩子，按 `optional` 输出可选或强制钩子提示。

## 执行步骤

1. **初始化**：在仓库根目录运行 `{SCRIPT}`，解析 `FEATURE_DIR` 与 `AVAILABLE_DOCS`。所有文件路径必须使用绝对路径。

2. **澄清意图**：基于用户输入和 spec/plan/tasks 中的信号，最多提出 3 个上下文澄清问题。问题必须会实质影响清单内容；如果用户输入已经明确，则跳过。

   优先澄清：
   - 清单领域：安全、性能、UX、API、部署、回滚等
   - 使用者：作者自查、PR 审阅者、QA、发布门禁
   - 深度：轻量 sanity check、标准审查、正式发布门禁
   - 边界：哪些场景明确不在本轮检查中

   如果无法互动，默认使用：
   - 深度：标准
   - 使用者：代码相关时默认为 PR 审阅者，否则默认为作者
   - 重点：相关性最高的 2 个风险领域

3. **加载功能上下文**：
   - `spec.md`：需求和范围
   - `plan.md`：技术约束和依赖（如存在）
   - `tasks.md`：实现任务（如存在）

   只加载与当前清单领域相关的片段，不要转储全文。

4. **生成清单文件**：
   - 在 `FEATURE_DIR/checklists/` 下创建清单。
   - 文件名使用简短领域名，例如 `ux.md`、`api.md`、`security.md`。
   - 如果文件不存在，从 `CHK001` 开始编号。
   - 如果文件已存在，保留原内容，并从已有最大编号继续追加。

5. **编写清单项**：

   每个清单项都必须检查需求本身，而不是检查实现行为。优先覆盖：

   - **完整性**：必要需求是否都已写出？
   - **清晰度**：表述是否无歧义、足够具体？
   - **一致性**：不同章节之间是否冲突？
   - **可衡量性**：是否能客观判断达成？
   - **场景覆盖**：主流程、备选流程、异常流程、恢复流程和非功能场景是否覆盖？
   - **依赖与假设**：外部依赖、前提和风险是否明确？

   推荐格式：

   ```markdown
   - [ ] CHK001 是否为所有失败模式定义了错误处理需求？[Gap]
   - [ ] CHK002 “快速加载”是否被量化为明确时间阈值？[Clarity, Spec §NFR-2]
   - [ ] CHK003 导航要求在所有页面之间是否一致？[Consistency]
   ```

   禁止写成：

   ```markdown
   - [ ] CHK001 验证页面显示 3 张卡片
   - [ ] CHK002 测试悬停状态正常
   - [ ] CHK003 确认点击 logo 返回首页
   ```

6. **结构要求**：
   - 使用 `templates/checklist-template.md` 的标题、元信息、分类标题和编号格式。
   - 如果模板不可用，使用 H1 标题、用途/创建时间元信息，以及 `##` 分类章节。
   - 至少 80% 的清单项应包含追踪引用，如 `[Spec §FR-001]`、`[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]`。

7. **结果汇报**：
   - 输出清单文件完整路径。
   - 输出新增条目数量。
   - 说明是新建文件还是追加到已有文件。
   - 简述本次覆盖的领域、深度、使用者和用户明确要求。

## 执行后检查

**检查扩展钩子（生成清单之后）**：

- 如果 `.specify/extensions.yml` 存在，读取 `hooks.after_checklist`。
- YAML 无法解析时静默跳过。
- 过滤 `enabled: false`。
- 不要解释或求值 `condition`。
- 对每个可执行钩子，按 `optional` 输出可选或强制钩子提示。
- 如果没有钩子或文件不存在，则静默跳过。
